1.1Software Har Jagah Hai — Aur Isliye Bugs Mehenge Hain

Ek second ke liye aankhein band karo aur dekho — phone, watch, microwave, debit card ka chip, traffic light, lift, car ka GPS, bank ka app, hospital ka radiation machine — sab software chala rahe hain. Software aaj kal modern life ka invisible nervous system hai. Hardware body hai, software wo hai jo decide karta, react karta aur seekhta hai. Jab nervous system fail ho jata hai, body galat behave karti hai.

Isliye ek galat line of code ka matlab sirf "mere laptop pe program crash ho gaya" nahi hai — wo rocket crash karwa sakta hai, radiation dose galat calculate kar sakta hai, bank account khaali kar sakta hai. Course teen iconic disasters yaad karwata hai, aur ye MCQ me directly poochhe jaate hain:

✦ Story Mode — Teen Disasters Jo Ratta Maarne Layak Hain

1. Ariane 5 Rocket (June 1996, ESA). Dus saal ka mehnat aur crores ka paisa — 36 seconds me khatam. Kya hua? Ek routine 64-bit floating point number ko 16-bit signed integer me convert kar rahi thi. Number overflow ho gaya, exception utha, inertial reference system band — aur backup system me same code tha, to wo bhi same tarike se fail ho gaya. Rocket self-destruct.

2. Therac-25 Radiation Machine (mid-1980s). Concurrent threads ke beech race condition ki wajah se galat command combination possible ho gaya. Kai cancer patients ko massive radiation overdose mila; kuch ki maut hui. Fault hardware me nahi — software ke concurrent control logic me tha.

3. Intel Pentium FDIV Bug (1994). Floating-point division me lookup table ka bug. Ek mathematician ne pakda, aur Intel ko chips recall karni padi — estimated $475 million ka nuksaan.

✦ Yaad Rakho — Disaster ↔ Cause Mapping

Ariane 5 → data conversion / overflow (backup me same bug). Therac-25 → race condition / concurrent threads. Pentium FDIV → floating-point arithmetic error. PYQ pattern: "Which of the following is a famous example of a software failure?" — teeno me se koi bhi option aa sakta hai.

1.1.1 Bug Jitna Late Pakda Jaye, Utna Mehenga

Empirical data kehta hai — defect fix karne ki cost jitna late pakdo, utni exponentially badhti hai. Requirements phase me pakda hua bug lagbhag free hai. Wahi bug agar production (post-deployment) me pakda, to cost thousands of times zyada ho sakti hai. Rough rule: har next phase pe cost ≈ 10× ho jati hai. Isi liye "test early and often" bola jata hai.

1.1.2 Facts vs Myths

FactKyun matter karta hai
Testing errors dhundhti hai; correctness proving nahi kar sakti"Saare tests pass" ka matlab "koi bug nahi" nahi hai. Dijkstra: testing presence of bugs dikhata hai, absence kabhi nahi.
Alag-alag techniques alag-alag errors pakdti hainIsliye testing ko reviews / inspections / static analysis ke saath pair karna padta hai.
Test execution automate ho sakta hai, test design nahiTools tumhari requirements guess nahi kar sakte — design me human judgement chahiye.

1.2SDLC — Software ka Zindagi Chakra

◈ Samajh

Ghar banane ka socho. Bricks utha ke seedha stacking shuru nahi karte — pehle plan, phir design, phir build, phir inspection, phir keys handover, aur baad me maintenance. Software ka bhi same recipe hai, jise Software Development Life Cycle (SDLC) kehte hain. International standard jo isko define karta hai: ISO/IEC 12207.

SDLC ke 6 phases:

  1. Planning & Requirements — kya banana hai, kaun use karega, kya-kya feature chahiye. Output: SRS (Software Requirements Specification) + project plan.
  2. Design & Architecture — kaise banega: classes, modules, layers, database, protocols. Output: design documents, UML models.
  3. Implementation (Coding) — actual source code, coding guidelines follow karte hue. Agile me developer saath-saath unit tests bhi likhta hai.
  4. Testing — verify karo ki jo bana wo wahi hai jo specify hua tha, aur sab situations me sahi behave karta hai.
  5. Deployment / Release — customer ko handover ya production me live.
  6. Maintenance — production bugs fix karna, naye features, naye platforms.

1.3Testing ki Vocabulary — Yahan Sab Confuse Hote Hain

1.3.1 Verification vs Validation — Har Quiz Ka Pakka Sawaal

◈ Samajh

Validation poochta hai: "Kya hum sahi product bana rahe hain?" — kya ye sach me user ka problem solve karta hai? Verification poochta hai: "Kya hum product ko sahi tarike se bana rahe hain?" — kya har phase ka output us phase ke shuru me promised requirements se match karta hai?

✦ Memory Trick

Validation → what the user wanted (user-facing). VeriFication → Follows the specification. Ek aur hook: verification me "F" hai — "Follows specs", validation me "L" hai — "looks like what user wanted".

VerificationValidation
SawaalAre we building the product right?Are we building the right product?

1.3.2 Static vs Dynamic Testing

Static testing = artefact ko bina chalaye examine karna: code reviews, inspections, walkthroughs, static analysis tools, formal verification (model checking, theorem proving, symbolic execution). Dynamic testing = code ko inputs ke saath execute karke behaviour dekhna. Verification usually static, validation usually dynamic.

1.3.3 Fault, Error, Failure — F.E.F. Chain

Ye teen words log interchange kar dete hain, lekin IEEE/ISTQB glossary inko precisely alag rakhta hai — aur quiz me exact distinction poochha jata hai:

✦ Definitions — Word by Word

Fault (defect, bug) — software me ek static flaw: missing code, galat condition, off-by-one. Ye source me sota rehta hai (dormant).

Error — fault execute hone par bane galat internal state: variable me ab galat value hai, lekin abhi kisi ne notice nahi kiya.

Failure — externally visible galat behaviour: user ne kuch galat dekha — crash, screen pe galat number, missing feature.

◈ Samajh — Car Wali Kahani

Car ke brake pads me manufacturing defect hai (fault). Normal din pe kuch nahi hota. Ek barsaati raat brake dabaya, ghisa pad slip hua aur wheel andar se lock ho gayi (error — car ab galat internal state me hai). Driver ko car skid karti dikhi (failure — externally visible). To chain bani: fault → (execution) → error → (propagation) → failure.

1.3.4 RIPR Model — Failure Dikhne ke liye Kya-Kya Chahiye

Ek fault se observable failure tak pahunchne ke liye 4 cheezein honi chahiye:

  1. Reachability — test case ne buggy location ko execute kiya (wahan pahuncha).
  2. Infection — execute karne se program state galat ho gayi (variable me galat value).
  3. Propagation — wo galat state output tak propagate hui (observable output galat).
  4. Reveal — us output ko actually check kiya gaya (warna tester miss kar dega).

Pehle teen = RIP model; fourth ke saath = RIPR model (Ammann & Offutt). Ye course ka favourite hai.

✦ Exam Tip

Pattern: "A test executes the buggy line but the test passes. Which RIP step failed?" — jawab: infection (fault pahuncha par state corrupt nahi hui) ya propagation (state corrupt hui par output tak nahi pahunchi). Aur agar output check hi nahi hua — reveal.

1.3.5 Levels of Testing — Pyramid

✦ Yaad Rakho — Memorisation Drill (Matching PYQ)

Unit testing — developer, coding ke dauran, smallest unit isolation me. Integration testing — kai components ko jodkar unke interfaces test karna. System testing — full implementation ko us platform ke saath test karna jahan wo chalega. Acceptance testing — end customer, committed requirements confirm karne ke liye (alpha = in-house, beta = external users).

1.3.7 Beizer ki Test Maturity Levels — Har Paper Me Aata Hai

Boris Beizer ne organisations ko 5 levels me baanta — har level ka belief yaad rakho:

LevelOrganisation ka beliefKeyword (question me dikhega)
0Testing aur debugging me koi difference nahi."no difference"
1Testing ka purpose hai show correctness — ki software works."show it works / correctness"
2Testing ka purpose hai show that software does not work — bugs dhundhna."show failures", adversarial relationship

⚠ Dhyan — Sabse Bada Trap

Level 1 positive sunta hai ("show correctness") lekin wo actually naive hai — organisation ye maan raha hai ki testing se correctness prove ho sakti hai (jo impossible hai). Level 2 zyada mature hai (failures dikhana), Level 3 usse bhi zyada (risk reduction), Level 4 sabse mature.

Dusra trap: "minimum" vs "maximum" maturity. "Testers-developers cooperate to reduce risk" → minimum Level 3. "Testers adversarial relationship me hain, sirf failures dhundhte hain" → maximum Level 2 (kyunki Level 3+ me cooperation hota hai). Question ka wording dhyan se padho!

1.3.8 Four Major Test Activities

Ammann & Offutt ke hisaab se test work ke 4 activities:

  1. Test design — kya test karna hai (test requirements, test cases). Sabse intellectual kaam; human chahiye.
  2. Test automation — test cases ko executable scripts banana (JUnit, PyTest, Selenium…).
  3. Test execution — tests ko actually chalana (often CI ke through).
  4. Test evaluation — results padhna, faults isolate karna, coverage compute karna, defect reports dalna.

Ek related classification (kuch PYQs me): Test requirement → Test specification → Test case → Test script.

1.3.9 Test Case ki Anatomy

✦ Definition

Ek test case ek tuple hai: $(prefix,\ test\ input,\ expected\ output,\ postfix)$. Prefix values system ko required state me le jaati hain (DB connection kholna, object banana). Test inputs unit ko diye jaane wale actual values. Expected output specification se derive hota hai. Postfix values state clean-up karti hain (connection band karna).

Test oracle = wo mechanism jo actual output ko expected se compare karta hai (jaise JUnit ka assertEquals).

✦ Exam Tip

Repeated PYQ: "What is required to create a test case?" — Test inputs + expected outputs. Actual outputs execution ke BAAD milte hain, isliye wo test case banate waqt nahi hote.

1.3.10 Test Requirement vs Coverage Criterion vs Test Path

✦ Definitions

Test requirement (TR) — ek specific cheez jo test ko satisfy/cover karni hai (e.g. "node 5 visit ho", "edge (3,7) exercise ho").

Coverage criterion — ek rule jo artefact se TRs ka set banata hai (e.g. "Node Coverage" → saare reachable nodes).

Coverage — diye gaye test set dwara satisfy kiye gaye TRs ka fraction (%) .

Workflow yaad rakho: Coverage criterion → test requirements → test cases → test scripts.

✦ Exam Tip — Jan 2026 me aaya

"Difference between test requirements and test cases?" — Correct: "Test requirements represent the required coverage criteria, whereas test cases define an execution to satisfy one or more of those requirements." TRs abstract hote hain (criteria se pehle banate hain), TCs concrete executions hote hain. TR–TC interchangeable nahi, aur TR execution ke baad nahi bante.

1.4Test Automation & JUnit — Zero se

Practical software me hazaaron test cases hote hain. Har change ke baad unhe haath se chalana impossible hai — isliye execution automate karte hain: ek tool har test chalata hai, actual vs expected compare karta hai, aur pass/fail report deta hai. Test design automate nahi hoti — execution hota hai.

1.4.1 JUnit Kya Hai?

JUnit Java ka open-source unit-testing framework hai (current version JUnit 5 / Jupiter). Ye deta hai: @Test jaise annotations, assertion methods (test oracle), lifecycle hooks (@BeforeEach…), aur ek test runner jo har @Test method dhundh ke chalata hai.

◈ Samajh

JUnit ek school exam ka answer-key checker jaisa hai: teacher (developer) sirf questions (test methods) aur model answers (assertions) likhta hai; checking mechanical hai — har assertion pe green tick ya red cross.

1.4.2 Java Refresher + Pehla JUnit Test

JUnit padhne se pehle 3 Java concepts: Class (data + behaviour ka blueprint), Method (ek kaam karne wala named block), Object/Instance (class ka concrete entity, new se banta hai).

Calculator.javacode base
public class Calculator {
    // method jo do integers ka sum return karta hai
    public int add(int a, int b) {
        return a + b;
    }
}
CalculatorTest.javajunit hello world
import static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.api.Test;

class CalculatorTest {
    private final Calculator calculator = new Calculator();

    @Test

Line by line: import static ...assertEquals — assertEquals bina prefix ke likhne ke liye. @Test — neeche wali method ek test hai. calculator.add(2, 3) — test input. Pehla argument 5 — expected output (specification se aaya). assertEquals(expected, actual) — test oracle; mismatch hone par test fail.

1.4.4 Test Fixtures

Test fixture = wo state jo ek ya zyada tests ko chahiye — e.g. khaali list, DB connection. Fixture objects ko instance variables banao, @BeforeEach me initialise karo (har test se pehle fresh milta hai, isliye tests state share nahi karte), aur @AfterEach me reset karo.

private List<String> list;   // fixture (instance variable)

@BeforeEach
public void setUp() {
    list = new ArrayList<String>();   // prefix: fresh list
}

@AfterEach
public void tearDown() {
    list = null;                      // postfix: clean up
}

1.4.5 Common Assertions + Expected Exception

AssertionPass hota hai jab…

Expected exception — do patternsjunit 4 vs junit 5
// Pattern A (legacy, JUnit 4 style)
@Test
public void testForNullList() {
    list = null;
    try {
        Min.min(list);
        fail("NullPointerException expected");   // agar yahan pahunch gaye = fail
    } catch (NullPointerException e) {
        // pass: humne yahi expect kiya tha
    }
}

// Pattern B (JUnit 5 — much cleaner)
@Test
void testForNullList() {
    assertThrows(NullPointerException.class, () -> Min.min(null));
}
⚠ Dhyan — Java/JUnit ke Famous Traps (PYQ Favourites)

1. String comparison: assertTrue(s1 == s2) Strings ka reference compare karta hai — textually equal Strings bhi fail ho sakte hain. Value ke liye assertEquals(s1, s2) ya s1.equals(s2).

2. assertNull on primitive: assertNull(-1) — int auto-box hoke Integer(-1) ban jata hai jo kabhi null nahi hota — assertion hamesha fail.

3. Self-assignment bug: setter me state = state; likh diya (this.state = state ki jagah) — field kabhi update nahi hoti.

4. Off-by-one loops: for(i=1; …) index 0 skip; i < arr.length - 1 last element skip; i <= arr.length overrun.

5. Predicate inversion: % 2 == 1 likh diya jabki even check karna tha (% 2 == 0) — meaning silently invert.

6. Implicit super(): subclass constructor me explicitly super(...) na likho to Java chupchaap super() daal deta hai — parent fields default values le leti hain.

7. Bug masking: off-by-one bug tab tak expose nahi hota jab tak expected last value default (0) ke barabar na ho. Isliye boundary element ko distinctively non-zero rakho.

2.1Graph Basics

2.1.1 Graph Theory Kahan Se Aayi? (Königsberg)

1736 me Euler ne poochha — kya Königsberg shehar ke 7 bridges ko har ek exactly ek baar paar karke walk possible hai? Jawab: nahi. Aur is sawaal ne graph theory ko janam diya. (Trap: 1736 hai, 1976 nahi!)

✦ Formal Definition

Graph ek pair hai $G = (V, E)$ jahan $V$ finite non-empty vertex (node) set hai aur $E \subseteq V \times V$ edge set hai. Directed graph (digraph) me edges ordered pairs hain — $(u,v) \ne (v,u)$. Self-loop = node se wapas usi node pe edge.

Degree concepts: undirected me degree = incident edges. Directed me in-degree (andar aane wali edges) aur out-degree (bahar jaane wali edges).

Testing ke liye 2 extra sets: $N_0 \subseteq V$ = initial nodes (execution shuru ho sakti hai wahan; code graphs me $|N_0| = 1$), $N_f \subseteq V$ = final nodes (normal termination). Graph tabhi "testable" hai jab $N_0 \ne \emptyset$ aur $N_f \ne \emptyset$.

2.1.2 Paths, Length, Sub-paths

✦ Definitions

Path = nodes ki sequence $[n_1, n_2, \ldots, n_k]$ jahan har consecutive pair $(n_i, n_{i+1})$ graph ka edge hai. Length = edges ki ginti = $k-1$. Single node $[n]$ = length 0 ka path. Single edge $[a,b]$ = length 1.

Sub-path = path $p$ path $q$ ka sub-path hai agar $p$, $q$ ke andar contiguous (lagataar) segment ho.

2.1.3 Test Paths — Syntactic vs Semantic Reachability

✦ Definition

Test path = aisa path jo kisi $n_0 \in N_0$ se shuru hoke kisi $n_f \in N_f$ pe khatam hota hai.

Node/edge syntactically reachable hai agar graph me wahan pahunchne ka path exist karta hai (paper pe possible). Semantically reachable (feasible) hai agar koi real input value program ko us path pe le jaye. Paper pe path ho par koi input use na chala sake → path infeasible hai. Example: path jisme ek hi $x$ ke liye $x > 0$ aur $x < 0$ dono chahiye.

2.1.4 Tours, Sidetrips, Detours — Har Paper Ka Favourite

✦ Definitions (Ratta!)

Test path $p$, sub-path $q$ ko tour karti hai agar $q$, $p$ ka hi hissa (contiguous sub-path) ho.

Sidetrip at $n_i$ — $p$, $q$ se node $n_i$ pe deviate hoti hai, ghumti hai, aur wahi wapas $n_i$ pe aake continue karti hai. (Side = Same node par return.)

Detour from $n_i$ — $p$, $n_i$ se deviate hoti hai aur kisi later node $n_j$ pe wapas join karti hai (beech ke nodes skip). (Detour = Different/later node par re-entry.)

◈ Samajh — Chai Break Analogy

Office se canteen ja rahe ho (route $q$). Raste me paani peene 2 minute ke liye cooler tak gaye aur usko point pe wapas aake chal diye — sidetrip. Aur agar shortcut liya jo aage ke kisi point pe route me wapas mila — detour. Bas.

Correct statements: "Adjacency list representation provides a compact way to represent sparse graphs" ✓ aur "Adjacency matrix representation provides a compact way to represent dense graphs" ✓. Galat: "matrix CFG ke liye use nahi ho sakta" ✗ / "list CFG ke liye use nahi ho sakta" ✗ — dono representations kisi bhi graph ke liye use ho sakti hain!

BFS level-by-level explore karta hai (queue use hota hai) aur shortest path (fewest edges) deta hai. DFS gehrai me jata hai (recursion/stack), aur iske upar cycle detection, topological sort, SCC bante hain. Dono ka runtime adjacency list pe $O(|V| + |E|)$ hai; adjacency matrix pe $\Theta(|V|^2)$. Connectivity: undirected graph connected hai agar har node har node se reachable ho. Directed graph strongly connected agar har $u$ se $v$ aur har $v$ se $u$ path ho. Sirf underlying undirected graph connected ho to weakly connected.

✦ Exam Tip — Jan 2026 me aaya

"Test paths for NC and EC can be obtained by simple modifications to BFS" — TRUE. BFS se saare reachable nodes (NC) aur edges (EC) cover karne wali test paths ban sakti hain. Aur back edge = ancestor se judne wali edge (cycles ka signal).

2.3Structural Coverage Criteria — Course ke Stars

✦ General Form

Coverage criterion $C$ graph $G$ se TRs ka set banata hai: $TR(C, G)$. Test set $T$, $C$ ko satisfy karti hai agar har TR kisi na kisi test path dwara tour ho jaye.

CriterionTR kya haiEk line me
Node Coverage (NC)Har reachable nodeHar node kisi test path se visit ho.
Edge Coverage (EC)Length ≤ 1 ke saare paths (effectively har edge)Har edge exercise ho.
Edge-Pair Coverage (EPC)Length ≤ 2 ke saare paths (har consecutive edge-joṛi)Har $a \to b \to c$ combo cover ho.
Prime Path Coverage (PPC)Saare prime paths (maximal simple paths)Har maximal simple route cover ho.
Complete Path Coverage (CPC)Saare possible test pathsLoops me infinite — practically infeasible!
⚠ Dhyan — EC "Length ≤ 1" kyun?

EC ko "paths of length up to 1" define kiya jata hai, sirf "every edge" nahi — taaki EC subsumes NC (length-0 path = single node). Warna kisi unreachable isolated node wale graph me 100% edge coverage ho jati jabki node kabhi visit hi na ho.

2.3.1 Worked Example — Diamond CFG

NC: $TR_{NC} = \{1, 2, 3, 4\}$ — test paths $t_1 = [1,2,4]$, $t_2 = [1,3,4]$ — done. EC: $TR_{EC} = \{(1,2), (1,3), (2,4), (3,4)\}$ — wahi dono paths saari edges bhi cover karte hain. EPC: length-2 paths = $\{(1,2,4), (1,3,4)\}$ — phir wahi 2 paths! (Is chhote graph me EPC free me ho gaya; bade graphs me extra paths lagte hain.)

2.3.2 Simple Paths & Prime Paths — Sabse Zyada Poochha Jane Wala Concept

✦ Definitions — Dhyan Se

Simple path = path jisme koi node do baar na aaye — except ki first aur last node same ho sakte hain (simple cycle allow hai). Isliye $[1,2,3,1]$ simple hai (first = last), lekin $[1,2,1,3]$ simple nahi (1 beech me repeat hua).

Prime path = aisa simple path jo kisi aur simple path ka proper sub-path na ho — yaani maximal simple path (na aage extend ho sake, na peeche).

Prime Path Coverage (PPC) = har prime path kisi test path dwara tour ho jaye.

◈ Samajh

Prime path "maximum-coverage route" hai — isse aage badho to node repeat hota hai ya graph khatam. PPC loops ko bhi cover karta hai: har cycle $[n, \ldots, n]$ ke form ka prime path ban jata hai. Linear chain $1 \to 2 \to 3 \to 4$ me sirf EK prime path: $[1,2,3,4]$ — baaki saare sub-paths uske andar hain.

2.3.3 Worked Example — Prime Paths Nikalna

Solution: Har node se simple paths gino, phir jo kisi bade simple path ke andar aa jaye use hatao:
• 1 se: $[1,2,3]$, $[1,2,4]$; $[1,2,3,2]$? — 2 interior repeat ✗… lekin cycle close hone par $[1,2,3,2]$ first≠last hai — hmm, is path me 2 do baar hai (position 1 aur 4) aur first node 1 hai — strict simple nahi. Lekin extension $[1,2,3,2]$ me dekho — actually ye wahi "1 se shuru hoke cycle 2-3-2 pe band hone wala" route hai. Course ke examples me aise paths ko maximal mane jate hain jab first node repeat na ho. Safest approach: extension rule follow karo — path tab tak extend karo jab tak (i) naya node mile ya (ii) first node wapas mile (cycle close).
• Final prime paths: $[1,2,3,2]$, $[1,2,4]$, $[2,3,2]$, $[3,2,3]$, $[3,2,4]$.
• Minimum test paths (tour all): $\{[1,2,3,2,4],\ [1,2,4]\}$ — 2 paths kaafi hain.

2.3.4 Round-Trip Coverage

✦ Definitions

Round trip = aisa prime path jiska first node = last node (yaani cycle).

Simple Round Trip Coverage (SRTC): har aise reachable node ke liye jo kisi round trip ko start/finish karta hai, TR me ek round trip rakho.

Complete Round Trip Coverage (CRTC): TR me har round trip rakho.

2.3.5 Subsumption Lattice — Poori Course Ka Sabse Quizzed Diagram

Subsumption: $C_1$ subsumes $C_2$ agar har test set jo $C_1$ satisfy kare, wo $C_2$ bhi automatically satisfy kare. Matlab $C_1$ "kam se kam utna hi strong" hai. Stronger criterion ko satisfy karne se weaker free me ho jata hai.

⚠ Dhyan — Counterexamples Jo Yaad Hon

EC does not subsume EPC. Diamond ke 2 paths $[1,2,4]$, $[1,3,4]$ EC cover karte hain — aur us chhote graph me EPC bhi! Lekin bade graphs me EC wale paths kuch edge-pairs chhod sakte hain. NC does not subsume EC. Saare nodes visit karna saari edges visit karna guarantee nahi karta (parallel/extra edges ho sakti hain).

Course ki official line (2025–26 keys ke hisaab se): PPC subsumes NC, EC aur All-Uses — lekin EPC ko "subsumes" mat likho (EPC option hamesha ✗ marked mila hai). Aur CPC sabse strong hai lekin usually infeasible.

✦ Exam Tip — Sep 2025 + Jan 2026 se

Repeated MSQ: "PPC subsumes which criteria?" → All Uses Coverage ✓, Edge coverage ✓; Edge-pair ✗, Complete path ✗. Transitivity bhi yaad rakho: $C_3 \Rightarrow C_2 \Rightarrow C_1$ ho to $T_3$, $T_1$ ko zaroor satisfy karega; ulta nahi.

2.4Algorithms — Prime Paths & Minimum Tests

2.4.1 Prime Path Enumeration Algorithm

  1. Har single node se shuru karo (length-0 simple paths).
  2. Har simple path $[n_1,\ldots,n_k]$ ko uske last node $n_k$ ke har neighbour $n_{k+1}$ se extend karo agar: (i) $n_{k+1}$ path me nahi hai, YA (ii) $n_{k+1} = n_1$ (cycle close — sirf ek baar).
  3. Jab extension possible na ho — path ko candidate prime path mark karo.
  4. End me jo candidates kisi bade candidate ke proper sub-path hain, unhe hatao. Jo bache = prime paths.

2.4.2 Minimum Test Set + Coverage Percentage

Minimum test paths dhoondhna set-cover type problem hai — heuristic: longest prime path pehle lo, use initial node tak peeche aur final node tak aage extend karo, phir dekho kaunse aur prime paths isi test path me tour ho gaye, unhe cross karo, repeat.

✦ Coverage Formula

$$\text{coverage}(T, C) = \frac{|\{tr \in TR(C) : \exists\, p \in T \text{ jo } tr \text{ ko tour kare}\}|}{|TR(C)|}$$

PYQ pattern: "given 3 test paths, NC/EC/EPC coverage kya hai?" — TRs satisfied gino ÷ total TRs.

2.4.3 Worked Example — While-Loop CFG

Kyun 3 tests? Edge-pairs hain: $(1,2,3), (1,2,4), (2,3,2), (3,2,3), (3,2,4)$. Path $[1,2,3,2,4]$ tours $(1,2,3), (2,3,2), (3,2,4)$ — missing: $(1,2,4)$ (need $n=0$) aur $(3,2,3)$ (need 2 iterations). Isliye total 3 test paths. Prime paths: $[1,2,4]$, $[1,2,3,2]$, $[3,2,3]$, $[3,2,4]$ (aur cycle $[2,3,2]$ inhi me samaa jata hai) — wahi 3 test paths PPC bhi satisfy karte hain.

✦ Week 2 — Quick Revision

Graph: $(V,E)$, directed, self-loops allowed; $N_0$ initial, $N_f$ final; test path = $N_0$ se $N_f$ tak.

Path concepts: simple path (first=last allowed) · prime path (maximal simple) · sub-path (contiguous).

Tours: direct · sidetrip (same node par wapas) · detour (later node par wapas).

Criteria (weak → strong): NC ≤ EC ≤ EPC ≤ PPC ≤ CPC. SRTC ≤ CRTC side chain me.

BFS/DFS: dono $O(|V|+|E|)$ adjacency list pe; BFS = shortest path, DFS = cycles/topo-sort; back edge = ancestor.

Algorithms: prime paths = enumerate + maximal; minimum tests = longest-first + extend + cross-off; coverage = satisfied/total TRs.

3.1Control Flow Graph (CFG)

✦ Definition

Method ki CFG ek directed graph hai jisme: Nodes = basic blocks (straight-line statements ka maximum group jo hamesha saath chalta hai), Edges = control transfer (sequence, if branches, loop back-edges). Exactly ek entry node aur kam-se-kam ek exit node.

◈ Samajh

CFG = program ka metro map. Har station ek basic block hai, har line ek possible train route. Coverage criteria wahi purane — bas ab "stations" statements hain aur "routes" control flows.

3.1.1 Har Construct Ka Pattern — Ratta Section

Rule 1 — Sequence: do statements aage-peeche = do nodes, ek edge.

3.1.2 Worked Example — Decisions + Loop Wala Method

compute.javacfg exercise
int compute(int n) {
    int s = 0;                        // node 1
    for (int i = 0; i < n; i++) {     // node 2 (init + test)
        if (i % 2 == 0)               // node 3
              s += i;                 // node 4
        else
              s -= i;                 // node 5
    }                                 // node 6 (step + back-edge)
    return s;                         // node 7
}

NC: 2 test cases — $n=2$ (dono branches: 4 phir 5) aur $n=0$ (seedha exit). Paths jaise $[1,2,3,4,6,2,3,5,6,2,7]$ aur $[1,2,7]$. EC: wahi 2 paths saari edges bhi cover karte hain. EPC: extra inputs lag sakte hain (jaise back-edge $(6,2)$ ke baad dono branches dekhna). PPC: cycles $[2,3,4,6,2]$, $[2,3,5,6,2]$ prime paths ban jaati hain.

✦ Exam Tip — CFG Questions Ka 3-Step Recipe

Jab "is CFG ke liye NC/EC/EPC/PPC satisfy karne wali test paths batao" aaye: (1) TRs list karo (nodes / edges / length-2 paths / prime paths). (2) Har TR ke liye ek path chuno jo initial se shuru hoke final pe khatam ho. (3) Paths merge karke count minimize karo. Bas yehi 3 steps har comprehension question me kaam karte hain.

3.2Data Flow Testing — Variables Ka Safar

◈ Samajh — Cargo Analogy

Har variable ko cargo samjho. Jahan value usme loaded hoti hai = definition (def). Jahan cargo padha jata hai = use. Control-flow coverage sirf ye batata hai ki stations gaye ya nahi; data-flow coverage check karta hai ki har loading point se har unloading point ka safar exercise hua ya nahi. Kai bugs isi safar me hote hain — variable define hui hi nahi, do baar define ho gayi bina use hue, ya galat order me.

✦ Definitions — def aur use

Definition (def) of $v$ = location jahan $v$ ko value assign hoti hai (variable "written"). Sources: assignment statements, method ke formal parameters (entry node pe defs), input statements.

Use of $v$ = location jahan $v$ ki value read hoti hai. Do flavours: c-use (computational — RHS of assignment, print) — node pe hota hai; p-use (predicate — if/while ki condition) — edge pe hota hai (kyunki decision 2 out-edges me se ek chunta hai).

Yaad rakho: defs nodes se judte hain; c-uses nodes pe, p-uses edges pe.

✦ Definitions — def-clear & du-path

Path $[n_1, \ldots, n_k]$, variable $v$ ke liye def-clear hai agar $v$, $n_2 \ldots n_{k-1}$ (internal nodes) me redefine na ho.

du-path for $v$ = simple + def-clear path jo $v$ ke kisi def se shuru hoke $v$ ke kisi use pe khatam ho. Teen conditions: (1) start pe def, (2) end pe use, (3) beech me koi redefinition nahi.

du-pair = (def, use) ka aisa jodi jiske liye kam-se-kam ek def-clear path exist karti hai.

⚠ Dhyan — Sabse Common Galti

du-path ke liye simple path hona zaroori hai — warna loops me koi bhi path arbitrarily extend hoti rahegi. Aur "def-clear" me redefinition usi variable ki honi chahiye — dusre variables ke assignments path ko todte nahi.

3.2.1 Teen Data-Flow Coverage Criteria

CriterionTR kya haiEk line me

4.1Integration Testing — Modules Ka Milap

◈ Samajh — Bolt Wali Kahani

Car ka engine perfect hai, wheels perfect hain (dono unit-tested). Lekin wheel ko axle se jodne wala bolt galat size ka hai — car nahi chalegi. Integration testing wahi bolts check karta hai: modules ke interfaces.

✦ Definitions — Coupling, Cohesion, Call Graph

Coupling = do modules ke beech dependency ki strength. High coupling = bura (modules ek-dusre ke bahut andar tak jaante hain, isolation testing mushkil). Low coupling desirable.

Cohesion = ek module ke andar ke elements ka aapas ka rishta. High cohesion = achha (module ek hi kaam karta hai). Design goal: low coupling + high cohesion.

Call graph = nodes methods/modules, edge $A \to B$ matlab "$A$, $B$ ko call karta hai". Integration tests isi graph pe plan hote hain — aur wahi coverage criteria lagte hain: NC = har method integrate-tested, EC = har call relation exercise ho, EPC = har call-triple ($A \to B \to C$).

4.1.1 Scaffolding — Stubs aur Drivers

Module $A$ module $B$ ko call karta hai, par $B$ abhi ready nahi? Ya $B$ ready hai par koi usse call karne wala nahi? Tab temporary scaffolding (maad) banate hain:

✦ Definitions — Ratta Maar Lo

Stub = kisi callee (called module) ka minimal skeletal replacement — $B$ ka "naqli" version jo hard-coded values return kare, taaki $A$ test ho sake. Stub = Substitute for the Subordinate (callee).

Driver = kisi caller ka minimal skeletal replacement — jo $B$ ko inputs feed kare aur usse call kare. Driver = jo unit ko Drive (call) karta hai.

Yaad-rakhne ka formula: Top-down needs STUBS · Bottom-up needs DRIVERS · Sandwich needs BOTH · Big-bang needs NEITHER.

4.4.1 Cyclomatic Complexity — McCabe (1976)

✦ Teen Equivalent Formulas

$$V(G) = E - N + 2P \qquad V(G) = (\text{binary decisions}) + 1 \qquad V(G) = (\text{bounded regions}) \text{ [planar drawing]}$$

$E$ = edges, $N$ = nodes, $P$ = connected components (single method ke liye $P = 1$, to $V(G) = E - N + 2$). $V(G)$ = linearly independent paths ki ginti = basis path testing me chahiye waali minimum test paths.

Exam me sabse fast formula: har if, while, for, ternary (?:) = 1 binary decision; sab jodo, +1 karo, done. Multi-method class ke liye $P$ = methods ki ginti, aur $V(G) = E - N + 2P$ (ya per-method complexities ka sum).

✦ Exam Tip — Speed Drills (Actual PYQ Answers)

Matrix multiply (1 if + 3 for) → $4 + 1 = \mathbf{5}$ (Jan 2025). Bubble sort (2 for + 1 if) → $3 + 1 = \mathbf{4}$ (2024 T3). Code with 1 if + 3 nested for → 5 (2025 T1). Sab me trick same: loops bhi decisions hain! Aur basis path fill-in-blank: "The number of linearly independent paths in a CFG represents the minimum number of paths required for basis path testing."

4.4.2 Basis Path Testing

✦ Definition

CFG ki cyclomatic complexity $V(G)$ ho, to $V(G)$ linearly independent paths ka basis chuno aur har ek test karo. Baaki HAR path in $V(G)$ paths ki linear combination hota hai. Isliye $V(G)$ = branch coverage ke liye minimum test cases ki ginti bhi hai.

✦ Exam Tip — May 2026 me aaya

"In which type of testing is the number of test requirements (TRs) equal to the cyclomatic complexity of the CFG?" → Basis Path Testing (PPC/EPC/data-flow me TR count alag hota hai).

4.4.3 DD-Paths — Decision to Decision

✦ Definition — Chain Se

Chain = aisa path jiske saare interior vertices ki in-degree = 1 AUR out-degree = 1 ho (beech me koi decision/join nahi), aur initial/terminal vertices distinct hon. Maximal chain = aisi chain jo kisi aur chain ka hissa na ho.

DD-path = maximal chain of length ≥ 1, YA single vertex jo in me se ek ho: (a) initial vertex (in-degree 0), (b) final vertex (out-degree 0), (c) decision vertex (out-degree ≥ 2), (d) join vertex (in-degree ≥ 2).

DD-path testing: seedhe stretches collapse karke reduced graph banate hain, uspe test paths banate hain.

⚠ Dhyan — DD-path Traps (Actual Key Statements)

✓ "It can be a single vertex with out-degree ≥ 2" (decision vertex). ✓ "It can consist of only the initial vertex" (in-degree 0). ✗ "Every chain is a valid DD-path" — sirf maximal chain DD-path banti hai. ✗ "It cannot consist of only the final vertex" — ulta, final vertex (out-degree 0) bhi single-vertex DD-path ho sakti hai! ✗ "Maximal chain of length ≥ 2" — length ≥ 1 hoti hai. ✓ "Interior vertices of a chain have in-degree = out-degree = 1" — isliye "interior vertices can have degree > 1" hamesha galat.

Master Cheat Sheet

Exam se pehle 10 minute — poori book ka saar ek page pe. Ratta section hai, padhne ka nahi.

◈ Subsumption Order

NC ≤ EC ≤ EPC ≤ PPC ≤ CPC — "Not Every Exam Paper Covers everything."

ADC ≤ AUC ≤ ADUPC (data flow spine)

AUC ⇒ EC · PPC ⇒ ADUPC (du-paths simple hain) · ADC ⇏ EC (trap!)

Course line: PPC ⇏ EPC (keys me EPC hamesha ✗)

Transitivity: strong ⇒ weak hamesha; weak ⇒ strong kabhi nahi.

◈ Cyclomatic Complexity

$$V(G) = E - N + 2P$$

$= (\text{binary decisions}) + 1$ — if, while, for, ?: sab = 1; else = 0

$= $ bounded regions (planar drawing)

Basis path testing = $V(G)$ independent paths · multi-method: $P$ = methods

Speed drills: matrix multiply (1if+3for) = 5 · bubble sort (2for+1if) = 4

◈ FSM Mapping

State coverage = Node coverage

Transition coverage = Edge coverage

Transition-pair = edge-pair · FSM = $(S, \Sigma, \delta, s_0, F)$

Sequencing constraints ka best model = FSM

CFG ≠ FSM (structure ≠ behaviour)

FIFO buffer (capacity $k$): reachable states = $k+1$ (prefix-fill), $2^k$ NahI!

◈ Stubs · Drivers · Strategies

Stub = callee replace (Subordinate) · Driver = caller replace (Drives)

Top-down = stubs · Bottom-up = drivers · Sandwich = dono · Big-bang = koi nahi

Top-down hierarchical ke liye accha hai (ulta statement = galat)

Interfaces: network request-resp = message passing · same-program call = procedure call · common memory = shared memory · common dict = shared data · file/device = external

Inter-procedural du-pairs: LDFU — Last Defined, First Used

◈ Beizer Levels (0–4)

L0 testing = debugging · L1 show correctness · L2 show failures (adversarial) · L3 reduce risk (cooperation) · L4 mental discipline (quality measured)

"cooperate + reduce risk" → min L3 · "adversarial + failures" → max L2 · "quality measure/improve" → L4

◈ F.E.F. + RIPR

Fault (static defect) → Error (wrong internal state) → Failure (external visible)

Match: Fault–2, Error–3, Failure–1 (external behaviour=1, static=2, state=3)

RIPR: Reach → Infect → Propagate → Reveal. Buggy line chali par test pass? = infection/propagation fail. Output check hi nahi hua? = reveal fail.

Disasters: Ariane 5 = overflow · Therac-25 = race condition · Pentium = FDIV

◈ TR Counting Recipes

NC: nodes gino · EC: edges gino · EPC: har edge $(a,b)$ ke aage $b$ ke har successor — final pe khatam hone wali edge se kuch nahi banta

PPC: simple paths enumerate (first=last allowed) → maximal rakhо; cycle ko initial-prefix karke kaunse variants count hote hain — options dekh ke decide karo

du-pairs: defs × uses me se jo def-clear route se judi hon · du-paths: distinct simple def-clear routes

Coverage % = satisfied TRs ÷ total TRs

◈ JUnit Yaad-list

@Test · @BeforeEach/@AfterEach · assertEquals(expected, actual) · assertThrows(X.class, …) · data-driven = @ParameterizedTest

Har test = ek test method · JUnit = unit testing framework (system ke liye nahi)

assertFalse(5 % 2 == 0) → PASS (5%2=1, 1==0 false)

s1 == s2 Strings = reference compare ✗ · assertNull(-1) = auto-box Integer, hamesha fail

◈ DD-path / Chain

Chain: interior vertices in-deg = out-deg = 1; initial ≠ terminal

DD-path = maximal chain (length ≥ 1) YA single vertex: initial (in-deg 0) / final (out-deg 0) / decision (out-deg ≥ 2) / join (in-deg ≥ 2)

"≥ 3 degree" wala option hamesha galat

◈ Graph Basics

$G = (V, E)$ · $N_0$ initial · $N_f$ final · test path = $N_0 \to N_f$

Simple path: first = last allowed, interior repeat ✗ · $[1,2,3,1]$ ✓ · $[1,2,1,3]$ ✗

Prime path = maximal simple path

Sidetrip = same node par wapas · Detour = later node par wapas (S-D)

Adjacency list = sparse (Θ(V+E)) · matrix = dense (Θ(V²)) · BFS/DFS = O(V+E)

DFS back edge = ancestor (cycles)

◈ Test Case + Levels

Test case = (prefix, input, expected, postfix) — banane ke liye inputs + expected chahiye (actual baad me)

Unit = developer · Integration = interfaces · System = full + platform · Acceptance = end customer

White-box: unit ✓ integration ✓ system ✓ · black-box: beta ✓ stress ✓ acceptance ✓

V-model: Req↔Acceptance · SysDesign↔Integration · DetailDesign↔Unit

Verification = sahi bana rahe (static) · Validation = sahi cheez bana rahe (dynamic)

◈ JUnit Bug Patterns (Failing Tests)

Off-by-one: i=1 se (index 0 skip) · i < len-1 (last skip) · expose hota hai jab last element positive/non-zero ho

Predicate inversion: % 2 == 1 vs == 0 — do bugs milke mask ho sakte hain ("galat reason se pass")

⚠ Top 10 Traps (Saare PYQs Se Nikale Gaye)
  1. Beizer "minimum vs maximum": wording dhyan se padho — cooperation = min L3, adversarial = max L2.
  2. Loops = decisions: cyclomatic complexity me for/while bhi 1-1 decision hain. Else = 0.
  3. Reach-the-error: x++ / y++ condition se pehle hua ya baad me — order check karo.
  4. assertion pehle evaluate karo: assertFalse(false) PASS hota hai. 5%2==0 → false → pass!
  5. du-path me redefinition: def-clear route me wahi variable dobara define ho to path "mar" jaati hai.
  6. EPC me final edges: final node pe khatam hone wali edge se naya edge-pair nahi banta.
  7. PPC EPC wale options: course ke hisaab se PPC ⇏ EPC — "subsumes edge-pair" option mat chunna.
  8. Prime path simplicity: interior repeat = simple nahi. $[1,3,5,3,4]$ type options pehle hi reject karo.
  9. FIFO buffer states: $2^k$ nahi — sirf prefix-fill wale $k+1$ reachable hote hain.
  10. Off-by-one masking: last element positive hona chahiye bug expose karne ke liye; expected=0 wale tests bug chhupa dete hain.
